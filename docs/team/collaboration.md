# 团队协作规范 · collaboration.md

> 面向本项目的多智能体协作。目标是**用流程消除沟通壁垒**，让一次改动就能通过门禁，
> 而不是靠事后互相对质。最近更新：2026-10-30 01:28:45（北京时间）

## 一、角色与命名

命名统一采用「**模块名（汉字）+ 团队**」，会话标识用小写拼音加 `-tuan`。

| 角色 | 会话标识 | 职责边界 |
|---|---|---|
| Lead（主理） | `lead` | **只做任务交办与最终核验**，不亲自改项目代码、不跑具体实现（用户规则 35） |
| 预设团 | `yushe-tuan` | 插件本体与预设实现的唯一写入者 |
| 体检团 | `tijian-tuan` | 只读取证与评估，**不改业务代码** |
| 回归团 | `huigui-tuan` | 门禁执行、真机验收、安装包出厂，只写日志与 `dist/` |
| 沟通团 | `goutong-tuan` | 面向用户的进度同步与团队基础设施，**不碰代码** |

## 二、任务板使用

1. **一个可交付物一张任务卡**。卡里必须写清：目标、必须覆盖的点、产出文件路径、写入范围、验收标准。
2. **先读后领**：`team_task_get` 读全文 → `team_task_update action=claim`（带最新 revision）→ 再动手。
   revision 过期会被拒，重新 `get` 拿最新值，不要猜。
3. **有顺序就写 `blocked_by`**，不要靠「等一下再问」来串联。被阻塞时不要开工。
4. **完工即 `complete`**，并在 `send_message` 给 Lead 时给出：改了哪些文件、门禁结果、遗留风险。
5. 卡里没写的范围**默认不许动**。

## 三、写入范围纪律

- 每张卡声明 `writeScopes`，**只在范围内写**。范围重叠是提醒不是锁，靠自觉 + 消息同步。
- 需要改别人的范围：先给该文件负责人发消息，确认后再动；或请 Lead 改派范围。
- **只读不写**的成员（体检团）连「顺手修一行」也不许——取证与修复必须分离，这是结论可信的前提。
- 报告类文档（`docs/repair-plan-*`、`repair-result-*`、`audit-*`）由**实现者本人**写，
  不让别人代笔，避免「实现与说明不一致」。
- **口头扩权不生效**：任何扩权（含 Lead 口头授权）必须在任务板上落地——要么 Lead 改 `writeScopes`，
  要么由执行者 `reopen → claim → edit` 补进描述与 `writeScopes`，并在汇报里注明「板上原值 vs 现 rev」。
  板上没落地就动手，等于越界；**先补 rev，再动手**。（2026-10-30 实例：Lead 口头说已扩展 `.gitignore` 范围，
  板上实际仍是原 3 项，由沟通团补至 rev6 后才动手。）

## 四、评审门禁（顺序不可跳）

改动完成后的标准流水线：

```
node --check <改过的 .mjs/.js>          # 语法
python -m py_compile <改过的 .py>        # 语法
node scripts/verify.mjs                  # 静态接线（人设/policy/工具参数/白名单/技能）
node scripts/test-preset-contract.mjs    # 用真实安装包的 Config schema 校验声明
node scripts/check-preset-mount.mjs      # 真实引导挂载（roster 必须非 broken）
powershell -File scripts/run-all-tests.ps1   # 全量回归（必须设超时 + 同步硬件监控）
powershell -File scripts/sync-install.ps1 -Pack   # 安装副本同步 + 打包预演
```

**门禁铁律**

1. **新测试必须先证明它会变红**：故意注入违规，确认测试失败，再恢复（HANDOFF §6.5）。
   变了不红的测试等于没写。
2. **失败必须可见**：禁止用 try/catch 吞异常、禁止自动降级、禁止重试掩盖真实缺陷（用户规则 1）。
3. **全量回归必须带超时**：超时即强杀，输出卡死位置与最后日志（用户规则 12）。
4. **测试必须并行起硬件监控**：CPU / 内存 / GPU / 显存 CSV 落 `logs/build/`（用户规则 7）。
5. **Warning / Error 立即修**：不积压、不带病进下一阶段（用户规则 11）。
6. **视觉交付必须验收**：带 Web GUI 面的改动要有可复核的观察记录，不得用「看起来没问题」代替（用户规则 6）。

### 四之一、验收证据必须可复核（三件套）

**门禁通过不能只写「PASS」。** 任何一处 PASS 都必须同时给齐三件东西，缺一件视为**未验收**：

| # | 要件 | 要求 | 反例（不合格） |
|---|---|---|---|
| 1 | **命令** | 人能原样复制执行的一整行，含工作目录与超时设置 | 「跑了 verify」 |
| 2 | **输出摘要** | 关键判定行的原文摘录（如 `verify: PASS (12 顶层键 / 661 行 patch)`）；失败时**全文**不截断 | 「全绿」「没问题」 |
| 3 | **日志路径** | 仓库内相对路径（或绝对路径）指向落盘文件，他人可直接打开核对 | 无路径 / 只贴终端截图 |

**书写模板**（最终交付说明沿用同一格式）：

```
[PASS] <门禁项名称>
  命令：node scripts/verify.mjs                     （工作目录：仓库根；超时 900s）
  摘要：verify: PASS (12 顶层键 / 661 行 patch)
  日志：logs/build/20261030-012907-baseline-verify.out.log
```

**判定规则**

- 三件套齐 → 记 PASS；缺任何一件 → 记 **UNVERIFIED（未验收）**，不得计入通过数。
- 只有「我确认过了」没有落盘的 → 一律 UNVERIFIED。**没有日志的 PASS 等于没跑**。
- 日志路径指向的文件必须真实存在且包含所述摘要；对不上按**伪造证据**处理，整条门禁重跑。
- FAIL 项同样三件套，且输出摘要用**失败原文全文**（用户规则 28），并附可复现命令。
- 超时强杀项要能看出「确实被杀」：给退出码（`124`）与最后日志原文（用户规则 12）。

### 四之二、交付物指纹必须自算（不得只靠转述）

**任何对外交付物（安装包 / tgz / 二进制 / zip）的字节数与哈希，必须由交付方自己跑命令实测。**
转述来的指纹只能当「待验证线索」，**不能直接当交付证据写进交付说明**。

- 命令模板：`Get-FileHash <path> -Algorithm SHA256`（PowerShell）／`sha256sum <path>`（Linux）。
- 记录六项齐全：**路径 + 文件名（含版本/日期）+ 字节数 + SHA-256 + runId + 冻结号**；缺一项即 UNVERIFIED。
- **交叉复核**：至少两个独立来源一致才可通过（如出品方自算 + 验收方自算）；
  不一致时**以文件实际哈希为准**，并追查是旧包、同名包还是重新打包导致。
- 理由：指纹是「用户拿到的那个文件」的唯一身份。转述链条越长，越容易张冠李戴。
- 实例（2026-10-30）：回归团报 `1,057,597` 字节 / `6C8EEB6C…EDCED`，
  沟通团独立 `Get-FileHash` 复算一致后才写入交付说明，并在文中标注「已独立复算」。

## 五、编码风格约定（写入即生效）

| 项 | 约定 |
|---|---|
| 模块格式 | **ESM**，入口 `index.mjs`；浏览器侧 `client.js` 同为 ESM |
| 缩进 | **2 空格**，不用 Tab；行宽以可读为准，不强制硬折行 |
| 注释 | 用**中文写「为什么」**，不复述代码在做什么；坑点标 `⚠️`，取舍标 `注意` |
| 字符串 | 单引号优先，模板串用于拼接路径/命令 |
| 依赖 | **零第三方依赖**（见 `deps/MANIFEST.md`），只用 Node/Python 标准库与宿主注入的 `@deepseek-ai/*` |
| 失败策略 | **fail-loud**：形状不符、缺字段、服务不存在 → 初始化即抛错暴露；不写「静默跳过」分支 |
| 硬编码 | 禁止针对样例/测试数据写死分支；身份、路径、枚举一律由数据源派生（用户规则 3） |
| 幂等 | 工具调用必须可重复执行，副作用（落盘、注册）要能吃重 |
| 函数规模 | 圈复杂度 > 10 或嵌套 > 3 层 → 拆分；但**禁止为缩短文件把高内聚逻辑切碎**（用户规则 26 / 30） |
| `.ps1` | 必须 **UTF-8 with BOM**；改完回查 BOM 是否还在（丢 BOM 会让整套测试起不来） |
| JSON 落盘 | 用 Python `utf-8` 写；不用 `Set-Content -Encoding UTF8`（会加 BOM 破坏 JSON） |
| 文档语言 | 面向用户的说明用中文、不用内部黑话；代码里的 why 注释也用中文 |

## 六、信息同步

- **唯一的用户通道是沟通团**：所有要告诉用户的话，写成 `docs/team/update-NN.md` 后经 Lead 转述，
  不允许各自直接向用户发消息，避免同一件事出现两种说法。
- **进度看板**：`docs/team/progress.md`（按北京时间记录阶段与证据路径）。
- **依赖变动**：`deps/MANIFEST.md`。
- **日志归档**：`LOGS-INDEX.md` 是总入口，阶段目录各有 README。
- 里程碑完成 → 一份 `docs/team/update-NN.md`（≤15 行、用户可读）；不做每日流水账。

## 七、时间基准

所有进度时间戳取**互联网北京时间**（`https://timeapi.io/api/Time/current/zone?timeZone=Asia/Shanghai`
为主源，苏宁 `https://f.m.suning.com/api/ct.do` 为备源）。取不到就在记录里写明「来源不可用」，
**禁止用本机系统时间冒充**（用户规则 24）。
