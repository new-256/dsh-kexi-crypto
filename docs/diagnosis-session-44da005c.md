## 二、已证实缺陷（P0）

### D1 · 符号未规范化，导致 20 币全部取数失败【根因】

`kexi-plugin.mjs:773-790` 只做 `.toUpperCase()`，从不补 `USDT` 计价后缀：

```js
if (args.symbol) syms.push(String(args.symbol).toUpperCase().trim())   // "BTC" 原样透传
...
else argv.push('--symbols', syms.join(','))                            // → fast_analysis.py
```

`fast_analysis.py:815-823` 同样只 `.strip().upper()`，无补全。而下游三个取数函数都要求完整交易对：

| 下游 | 出错位置 | 裸符号 `BTC` 的结果 |
|---|---|---|
| `CG_IDS.get("BTC")` | `fetch_klines.py:150-152` | 查不到（键是 `BTCUSDT`）→ `no CoinGecko id mapping for BTC` |
| Binance `?symbol=BTC` | `fetch_klines.py:91-92` | HTTP 400 → `request failed after 3 attempts` |
| OKX `instId=BTC` | `fetch_klines.py:108-114` | 缺连字符未转 `BTC-USDT` → 错误 51001 |

**本地实测**（同一台机器、网络正常）：

```
fetch_binance('BTC')     → HTTP 400, 9.38s（5 host × 3 retry 全跑满）
fetch_binance('BTCUSDT') → OK, 5 根, 0.61s
fast_analysis --symbol BTC → 29.35s, 评级【取数失败】
```

`20 币 × ~6s ≈ 120s`，与线上 `elapsed_ms=119636` 精确吻合。**证据链闭合。**

### D2 · 全源失败仍返回 `ok: true`（虚假成功）

`fast_analysis.py:894-897`：

```python
print(json.dumps({"ok": True, "count": len(rows), ...}))   # 恒为 True
return 0                                                    # 恒为 0
```

`kexi-plugin.mjs:799-803` 只要进程 exit 0 就 `return { ok: true, ... }`。

**后果**：调用方从结构化返回值拿到 `ok:true`，误判成功；失败信息只存在于人读的 digest 文本里。本次会话主理人正是被此误导，连续追加 6 次排障调用。

### D3 · 取数量级性能失控（无全局预算）

`fetch_klines.py:68` `retries=3, timeout=15` + `:64-65` 5 个 host + auto 模式再叠 OKX：

单币最坏 `5 host × 3 retry × (15s + 退避)`，**且错误符号必然跑满全部重试**。
对比：`datasources.py:145` 对新闻链路有 `NEWS_TIME_BUDGET_SEC=20` 预算，**K 线链路完全没有**。

## 三、已证实缺陷（P1）

### D4 · 产物被错误覆盖，`_position.json` 实为指标数据

实测 `kexi_out/` 中：

```
BTCUSDT_1d_indicators.json  SHA256 F8A61480…
BTCUSDT_1d_position.json    SHA256 F8A61480…   ← 完全相同
```

且该"position"文件**不含任何 `pos_90` / `drawdown` / `range_90` 字段**（字段列表为 `ma/ema/macd/rsi/volume/support_resistance…`，纯 indicator 内容）。

成因：某次 `kexi_run(mode=script, script="indicators.py", batch={args:[...,"--out","kexi_out/{item}_1d_position.json"]})` 传错了 `--out`，而**工具层对 `--out` 与 `script` 的不匹配零校验**，静默写成"position"文件名。

**风险**：后续 `position.py` 消费方若按文件名读取 `_1d_position.json`，拿到的是指标 JSON —— 位置/回撤/拥挤度全部失真或缺失，且**不会报错**。

### D5 · `CG_IDS` 为硬编码 15 币白名单，天然不可泛化

`fetch_klines.py:43-49` 仅 15 个 `*USDT` 键。任何白名单外币（新币、二线币）即使符号正确，CoinGecko 回退路径也必然失败。

> 违反用户规则 3（研发优先泛用方案禁硬编码）。此项**不是**针对测试样例"对答案"，但属同类投机实现。

### D6 · 编排规则全是"软提示"，无硬约束

- `kexi-plugin.mjs:1731` 规则第 0 步：「先调用 `kexi_ensure_team`」—— 只管**建队**，不管**用队**。
- `SKILL.md:199-202` 快速通道：「当用户仅需求'快速看看'时，无需五位成员全部登场」—— 门槛纯自然语言，**无判定代码**。
- 全会话**无任何代码**在检测「建了队但没派活」。

> **部分修正**：初版据第 1 轮判断"5 个成员全程空转"。完整跟踪后确认——**第 1 轮确实 0/5 派活，但第 2 轮 5/5 全员参与并成功收敛**。故本缺陷成立但**影响被初版夸大**：软提示在"高复杂度请求"下能被模型正确执行，只在"看起来简单"的请求（如仓位诊断）上失效。
>
> 真正的失效模式是：**复杂任务触发全员，简单任务（仓位诊断）完全绕过团队** —— 规则缺乏的是"何时必须用团队"的判据，而非"如何用团队"。

### D7 · 「仓位诊断」无工作流归属

`SKILL.md` 中 Workflow A~L 覆盖：单币研判 / 多币对比 / 应急复核 / 全市场筛选 / 打新 / 战绩 / CEX 调仓 / 保活 / Token / 消息面 / 入场时机 / 批量复核。

**「仓位诊断」不在任何一条触发条件内**。主理人自行作答属于规则空白，非违规——但意味着这类高频请求**完全绕过了五人分工体系**。

### D8 · Workflow D 触发词未覆盖实际问法

用户说「**我要选币，你给我挑10个**，注意分析一下当前整个大盘在什么行情」。

Workflow D 触发词为「全市场扫描 / 筛选潜力币 / 有什么币值得买」—— 「选币、挑10个」**未命中**。主理人虽自行推断为 Workflow D 并加载了 skill（`seq 73`），但代价是先走了 8 次单干排障。

### D9 · `wait_agent` 无降级兜底【结论推翻，改为已知风险】

初版称"会话终止于 `wait_agent(240000)` 处无结果、回答突然中断"。

**完整跟踪后推翻**：该现象是中途快照造成的误读。实际全会话共调用 `wait_agent` **9 次**，超时/返回正常交替，主理人在等待间隙主动并行工作（独立复算、交叉核验），并多次用 `list_agents` 探测成员状态。会话最终**正常走到 `turn/end`**。

**但仍有真实风险**：9 次 `wait_agent` 中有 **2 次返回 `{"timedOut":true}`**（`seq 207`、`seq 247`）。主理人此后的应对是"轮询 `list_agents` + 继续并行任务"，属**模型自发行为，非工具提供的兜底机制**。若模型未自发处理，仍会卡死。

### D10 · `kexi_run` 落盘快照滞后（本轮新发现，由成员实证）

数脉在 `seq 282` 回报：

> 「kexi_run 落盘层对 5 币存在源端快照滞后（**digest 新鲜但写盘文件止于 10-05**），已用直连交易所 API 补齐并修正 fetched_at，非标的停更。」

即：`kexi_run` 的 digest 显示数据是新鲜的，但实际写入 `kexi_out/` 的 JSON 文件内容停留在 10-05。**元数据与产物内容不一致**，且工具层不报错。

若成员未独立复核，这 5 个币（ADA/TRX/FIL/PEPE/PYTH）会被误判为"停更 13 天"而错误剔除——**事实上数脉 v1 正是这么判的**，靠主理人交叉核验才纠正（`seq 240`）。

**与 D4 同源**：二者都是 `kexi_run` 落盘层"产物内容与声明不符却零校验"。

### D11 · 团队反复出现"源端滞后"误判，暴露质检缺口

同一轮内连续出现两次同类误判：

1. 数脉 v1：把"源端快照滞后"误判为"标的停更 13 天"，建议弃用 5 币 → 被主理人独立复核否定（`seq 240`）
